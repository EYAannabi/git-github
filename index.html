PART 01

Setup on Windows

Install Git once, then tell it who you are. On Windows, run everything from Git Bash (installed together with Git) or from a terminal opened inside VS Code — both understand the Unix-style commands used throughout this guide (echo, cat, ls, mkdir, rm...).

Windows noteThere is no apt/apt-get on Windows — that's a Linux package manager. Install Git with the official installer or with winget, shown below.
01

Check if Git is installed

Open a terminal and ask for its version.

Terminal
git --version

If it's missing, install it with winget (PowerShell) or download the installer from git-scm.com:

PowerShell
winget install --id Git.Git -e --source winget
02

Open a terminal from VS Code

In VS Code: Terminal → New Terminal, then pick the Git Bash profile from the dropdown (top-right of the panel) so every command in this guide works as-is.

Verify the shell
pwd
git --version
03

Configure your identity (once, forever)

It will be attached to every commit you make.

Terminal
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
04

Confirm your configuration

Lists everything Git has stored globally.

Terminal
git config --list
PART 02

Create your first local repository

A repository is a folder that Git tracks. From that point on, Git remembers every version of every file inside it.

  1. Create and open your folder.
    Terminal
    mkdir my-first-project
cd my-first-project
  2. Initialize Git.

    This creates a hidden .git folder that will track the whole history of your files.

    Terminal
    git init
ls -la
  3. Create a file and check its status.
    Terminal
    echo "# My first project" > README.md
git status

    Git reports README.md as "untracked": it exists, but Git isn't watching it yet.

PART 03

The core cycle: add → commit

Three zones to remember: modified file → staging → saved commit.

1Working directoryYou edit your files
→
2Staging areaYou choose what to save
→
3RepositoryGit stores a version
01

Stage the file

Add it to the staging area, then check its state.

Terminal
git add README.md
git status

The file turns green — "Changes to be committed" — staged but not saved yet.

02

Save a commit

This is where Git permanently records a snapshot, with a message explaining the change.

Terminal
git commit -m "Add initial README"
03

Review the history

Every commit has a unique hash — a checkpoint you can always return to.

Terminal
git log
git log --oneline
PART 04

Edit, compare, repeat

The cycle repeats on every change: edit, inspect, stage, commit.

Exercise
echo "This is my very first Git project." >> README.md
git diff
git add README.md
git commit -m "Add a description to the README"

echo "recipe: ma9rouna kadheba" > recipe.txt
git add recipe.txt
git commit -m "Add a recipe"
git log --oneline

You should now see 3 commits in the history.

Remembergit diff shows changes that aren't staged yet — very useful for checking exactly what you're about to save. Run git status any time you're unsure where you stand.
PART 05

Undo a mistake

No panic — Git lets you roll back. Always double-check what you're about to undo before running these commands.

!

Careful
Undo commands can discard changes permanently. Only use them once you understand what they do.

Discard an unstaged change

Reverts the file to its last saved (committed) version.

Terminal
echo "test mistake" >> README.md
git status
git checkout -- README.md
cat README.md

The "test mistake" line is gone — the file is back to its last commit.

Undo the last commit

--soft undoes the commit but keeps your changes staged, ready to recommit — handy if you just got the message wrong.

Terminal
git log --oneline
git reset --soft HEAD~1
PART 06

Connect your repository to GitHub

Git works on your machine. GitHub hosts an online copy that your team can share.

  1. Create an account on GitHub (free).
  2. Create a new empty repository. Click the "+" button (top right) → New repository. Name it my-first-project and leave README and .gitignore unchecked — you already have a local project.
  3. Set up authentication (required since 2021 — GitHub no longer accepts plain passwords for Git). Two options:

Option A — HTTPS with a token

GitHub → your profile → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token. Check the repo scope, generate it, and copy the token — you won't see it again.

Option B — SSH (more convenient long-term)

Terminal
ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub

Paste the printed key into GitHub → Settings → SSH and GPG keys → New SSH key.

Link your local repository (pick one URL)

HTTPS
Remote
git remote add origin https://github.com/YOUR-USERNAME/my-first-project.git
SSH
Remote
git remote add origin git@github.com:YOUR-USERNAME/my-first-project.git
Verify and push
git remote -v
git branch -M main
git push -u origin main
Done!Refresh your GitHub repository page — you should see README.md and recipe.txt online.
PART 07

The daily cycle — and the difference between push and pull

This is the loop you'll repeat constantly. Memorize it.

1git statussee what changed
2git add filestage it
3git commitsave it locally
4git pushsend it to GitHub

Practical exercise

Terminal
echo "recipe: loubya bel k3aber" >> recipe.txt
git add recipe.txt
git commit -m "Add a second recipe"
git push

Now let's see the difference between push and pull

Step 1 — Edit a file directly on GitHub

On github.com, open your repository → click recipe.txt → click the pencil icon (Edit this file) → add a line:

New line
recipe: brikaaaa

Scroll down to "Commit changes", give it a title (e.g. "Add a recipe from GitHub"), and click Commit changes directly on main. You just created a commit straight on GitHub, without touching your PC.

Step 2 — Check your local machine (not synced yet)

Terminal
cd ~/my-first-project
cat recipe.txt

The "brikaaaa" line doesn't appear yet — your local repository has no idea about the change made on GitHub.

Step 3 — Fetch the change with git pull

Terminal
git pull
Expected output
remote: Enumerating objects...
Unpacking objects: 100%
From https://github.com/YOUR-USERNAME/my-first-project
   a1b2c3d..e4f5g6h  main       -> origin/main
Updating a1b2c3d..e4f5g6h
Fast-forward
 recipe.txt | 1 +
 1 file changed, 1 insertion(+)

cat recipe.txt now shows the "brikaaaa" line, pulled straight from GitHub.

In shortpush sends your local commits to GitHub. pull brings GitHub's commits down to your machine. They travel in opposite directions.
PART 08

Team exercise: clone, contribute, then personalize

Two very different situations in one exercise: contributing to a shared repository, versus keeping a personal, unshared customization. This is the distinction that trips people up most often — so we practice both back to back.

8.1 — Contribute to the shared project

SetupPick one contributor in the group. Everyone else is a sync participant. The shared repository for this exercise is EYAannabi/Linktree — replace it with your own if you're running this outside the workshop.
  1. The contributor clones the shared project into its own folder.
    Contributor's terminal
    cd ~
git clone https://github.com/EYAannabi/Linktree.git Linktree-contributor
cd Linktree-contributor
  2. The contributor adds a GitHub box.

    In index.html, add this block just before the closing </div> of the .links section:

    index.html
    <a href="#" class="link-box github">
  <span class="icon">💻</span> GitHub
</a>

    style.css already defines the .github class, so the box is styled automatically.

  3. The contributor saves and shares the change.
    Contributor's terminal
    git status
git add index.html
git commit -m "Add GitHub box"
git push
  4. Everyone else pulls the contribution into their own clone of the same shared repository.
    Other participants' terminal
    cd ~/Linktree
git pull
cat index.html

    The new GitHub box should now appear in your local copy.

Push

The contributor sends the change from their clone up to GitHub.

contributor's clone → GitHub

Pull

Everyone else brings that change down into their own clone.

GitHub → local clone

8.2 — Personalize your own copy (kept local, never shared)

Now the important nuance: from here on, personal links are never pushed to the shared repository — each person keeps their own version locally, then deploys it separately with GitHub Pages.

Step 1 — Customize your local copy

In ~/Linktree/index.html, replace the placeholder href="#" with your real links:

index.html
<a href="https://facebook.com/your-profile" class="link-box facebook">
<a href="https://instagram.com/your-profile" class="link-box instagram">
<a href="https://linkedin.com/in/your-profile" class="link-box linkedin">
<a href="https://github.com/your-profile" class="link-box github">
!

Do not git push this change to the shared repository — it's your private customization. Pushing it would overwrite the shared project with your personal links.

Step 2 — Deploy YOUR version on YOUR own repository

Since you don't want to pollute the shared repo with personal links, create a brand-new empty repository on GitHub for hosting (same steps as Part 6), then repoint your remote:

Terminal
cd ~/Linktree
git remote remove origin
git remote add origin https://github.com/YOUR-USERNAME/my-personal-links.git
git add .
git commit -m "My personalized version"
git push -u origin main

Step 3 — Turn on GitHub Pages for this new repository

On github.com/YOUR-USERNAME/my-personal-links: Settings → Pages → under "Source" pick branch main, folder / (root) → Save.

Step 4 — Visit your live site

After a minute or two, your site is live at:

Your site
https://YOUR-USERNAME.github.io/my-personal-links/
Mission accomplishedYou've now practiced both sides of real collaboration: contributing to a shared codebase, and keeping — then deploying — a personal fork without disturbing the team's repository.
PART 09

Branches: diverge, merge, resolve conflicts

A branch is a parallel version of your project, used to test changes without breaking main.

9.1 — Create a branch and push it

Terminal
cd ~/my-first-project
git checkout -b new-feature
echo "recipe: ojja" >> recipe.txt
git add recipe.txt
git commit -m "Add a recipe on a separate branch"

Git will suggest the exact push command for a brand-new branch:

Terminal
git push -u origin new-feature
What -u doesorigin is your remote's name (GitHub). -u (upstream) links your local branch to its remote counterpart, so future git push/git pull on this branch work without repeating origin new-feature every time.

9.2 — Visualize where you stand

Terminal
git log --oneline --graph --all
Example output
* 1c15b73 (HEAD -> new-feature) add ojja recipe
* 818fa1f Add a recipe on a separate branch
* 1738cc9 (origin/main) Add brikaaaa to recipe.txt
* 674e5f6 Add loubya bel k3aber
...

new-feature is 2 commits ahead of main — it contains work that main doesn't have yet.

9.3 — Confirm branches are isolated

Terminal
git checkout main
cat recipe.txt

Neither "kafteji" nor "ojja" appears here — proof that branches are genuinely isolated from one another.

9.4 — Create a real divergence

Make main evolve in parallel, so the two branches truly diverge from a common ancestor.

Terminal (on main)
echo "recipe: kafteji" >> recipe.txt
git add recipe.txt
git commit -m "Add kafteji on main"
git log --oneline --graph --all
Example output
* a1b2c3d (HEAD -> main) Add kafteji on main
| * 1c15b73 (new-feature) add ojja recipe
| * 818fa1f Add a recipe on a separate branch
|/
* 1738cc9 (origin/main) Add brikaaaa to recipe.txt
...

This is exactly what branching looks like: two development lines running separately from the same starting point.

9.5 — Merge new-feature into main

Terminal
git diff main new-feature
git merge new-feature
!

If both branches touched the same lines, Git can't merge automatically and inserts conflict markers:

Conflict example
<<<<<<< HEAD
recipe: kafteji
=======
recipe: ojja
>>>>>>> new-feature

Resolve it by hand: keep the content you want, delete the <<<<<<< / ======= / >>>>>>> markers, then finish the merge:

Terminal
git add recipe.txt
git commit -m "Merge new-feature into main"

9.6 — Verify the final result

Terminal
git log --oneline --graph --all
cat recipe.txt

All the recipes from both branches are now united in main.

9.7 — Push everything to GitHub

Terminal
git push
git push -u origin new-feature   # if not already done

9.8 — Clean up the merged branch

Terminal
git branch -d new-feature

-d refuses to delete a branch that has unmerged commits — a safety net. If it deletes without error, your merge genuinely succeeded.

PART 10

Protect secrets with .gitignore

An ignored file never shows up in git status or gets picked up by git add . — essential for passwords and temporary files.

10.1 — Without .gitignore: see the problem

Terminal
echo "DB_PASSWORD=supersecret123" > config.env
git status
Output
Untracked files:
  config.env

If you ran git add . now, config.env would be added and become publicly visible on GitHub the moment you push — a serious security mistake.

10.2 — Fix it with .gitignore

Terminal
echo "config.env" > .gitignore
git status

config.env no longer appears at all — Git ignores it completely, as if it didn't exist. Only .gitignore itself shows up as a new file.

10.3 — Commit the .gitignore (never the secret)

Terminal
git add .gitignore
git commit -m "Add gitignore to protect config.env"
git push

10.4 — Stress-test it

Terminal
git add .
git status

git add . — which normally stages EVERYTHING — still ignores config.env thanks to .gitignore. Even a careless add . can't leak your password.

On GitHub, .gitignore is listed in your repository, but config.env is nowhere to be found online — even though it still exists on your local disk.

10.5 — A few more useful patterns

.gitignore
*.log
__pycache__/
.env
config.env
ImportantIf a secret was already pushed to GitHub before being ignored, removing it from the file isn't enough — treat it as compromised and rotate it immediately.
PART 11

Cleaning up after the exercise

Once you're done practicing, you can remove the local folders you created.

Git Bash
cd ~
rm -rf my-first-project Linktree-contributor Linktree
Windows noterm -rf works in Git Bash out of the box. In PowerShell, use Remove-Item -Recurse -Force my-first-project instead.

Your GitHub repositories are untouched by this — delete them manually if you want, via Settings → Danger Zone → Delete this repository on each one.
